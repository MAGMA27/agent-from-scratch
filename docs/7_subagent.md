# subagent

采用主从 agent 架构，主 agent 可以启动多个子 agent 在后台进行复杂任务，所有任务由主 agent 统一分发和管理，系统整体行为更清晰，易于监控和调试。

适合：任务可以清晰分解为许多独立的、无需相互通信的子任务，并且对系统简单性、集中管理的要求高于对极致可靠性的要求。例如：批量数据处理、并行爬虫、多模型调用（LLM调用链）等。

不适合：任务需要从Agent之间频繁协商、实时协作或对高可用、低延迟有严格要求的场景。例如：实时多机器人协同控制、去中心化的市场模拟系统等。

# 实现

subgaent 的主要逻辑实现于 `myAgent/agent/subagent.py`，其中维护了一个 `SubagentManager` 类，复用了主 agent 的 `AgentRunner`，内部主要维护 `spawn`、`_build_tools`、`_run` 三个方法。

`spawn` 用于 subagent 的并发控制、子 agent 创建与销毁，`_build_tools` 负责给子 agent 构建工具，可以限定其工具视野，`_run` 负责用子 agent 的 spec 运行 agent loop，其结果会被传入输入消息队列，等待主 agent 消费。

将 `SubagentManager` 的 `spawn` 方法封装到 `myAgent/agent/tools/spawn.py` 中，作为 `tool` 暴露给主 agent，让它自主调度，参数为`task`（必须），`label`（非必须，subagent 的简洁描述）。

# 优点

1. 集中控制与协调简单：所有任务由主Agent统一分发和管理，避免了多个Agent之间复杂的直接通信。系统整体行为更清晰，易于监控和调试。

2. 任务分解与并行执行：主Agent可以将复杂任务拆解成多个独立的子任务，并分配给不同的从Agent并行处理，从而显著提高整体执行效率。

3. 专业分工明确：从Agent可以被设计为专门处理特定类型的子任务（如数据抓取、文本分析、图像识别等），易于开发和优化，且功能复用性强。

4. 结果汇总容易：主Agent集中收集所有从Agent的处理结果，进行整合、去重、冲突解决，最终形成统一、连贯的输出。

# 缺点
1. 单点故障风险：主Agent是整个系统的核心枢纽，一旦它出现故障、崩溃或网络中断，整个系统将完全瘫痪。

2. 性能瓶颈，扩展性受限：所有请求和响应都要经过主Agent，当从Agent数量增多或子任务高度密集时，主Agent容易成为系统的带宽或处理能力的瓶颈，导致吞吐量受限。一旦超过某个阈值，增加从Agent可能不会带来线性性能提升。

3. 灵活性不足：从Agent之间通常不能直接协作。如果某个子任务需要两个从Agent反复交互或迭代，这种架构会变得低效，必须通过主Agent中转，增加了延迟和通信开销。

4. 部署与维护复杂性：虽然协调逻辑集中在主Agent中看似简化了设计，但在实际部署中，需要额外保证主Agent的高可用（如主备切换、故障恢复机制），这增加了整体系统的复杂性。
