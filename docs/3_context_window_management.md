# 上下文窗口管理
由于 llm 本身没有记忆，所以上下文窗口管理在一定程度上就是 llm 的记忆管理。会话持久化保留了所有的对话记录 session，但只增不减的话，有超出上下文窗口限制、llm 性能恶化等风险。最基础的上下文窗口管理，不仅要时刻保持上下文在一定阈值内，给 llm 的回复留出余量，还要将超出阈值的对话记录压缩，避免缺失这部分“记忆”。

# nanobot 的三层记忆系统

## 1. session

第一层记忆系统就是 session，它是最细粒度的记忆，可以类比为短期记忆，保存每一条对话、tool call、tool result，非常具体，也很占上下文。

## 2. history

第二层记忆可以类比为中期记忆，它在上下文窗口预算不足时触发，或者定期触发，将具体的对话和 tool 内容压缩为一条 history，只保留目标、进度、决策、尚未完成的问题等，存在 history.jsonl 中。在组织上下文时，将一定范围的 history 加载，节约上下文窗口的同时保留之前的记忆。
通过 `MemoryStore` 管理记忆，用 `Consolidator` 进行压缩。

## 3. memory.md

第三层记忆属于长期的，本项目暂未实现。nanobot 开发了一个模块叫 `Dream`，它会定期消费 history 中的内容，并将其深度压缩为 memory.md 文件，在每次对话中加载，所有 session 共享。

# nanobot 的记忆系统设计哲学

nanobot 共享了所有的中长期记忆，也就是在不同的 session 中，nanobot 会知道前阵子做了什么，以前一起干了什么，但会丢失短期记忆。它能保留一个 agent 人格，记忆是"人格级别的长期积累"，不是"实时跨 session 同步"。

不过它也带来了一些问题，比如 history 压缩频率的矛盾，长了，跨 session 完全不知道最近做了什么；短了，在同一 session 对话时的信息损失可能过快，丢失了不久前做的事情的细节。同样的，`Dream` 的消费周期也有类似的问题。

可以通过在不同周期的记忆之间设定重叠区的方式，缓解这个问题，相应的，prompt 会更长，也会有重复信息，token 利用效率会有所降低。

```txt
Session A 的一条消息：
  ┌──────────────────────────────────────────────────────────────┐
  │ ① 原始态         ② 压缩摘要            ③ 长期记忆              │
  │ (session.jsonl)  (history.jsonl)       (MEMORY.md)           │
  │                                                              │
  │ 只有 Session A    全局共享              全局共享               │
  │ 自己能看到        其他 session 能看到    其他 session 能看到    │
  └──────────────────────────────────────────────────────────────┘
       ↑                    ↑                      ↑
   刚产生              Consolidator          Dream 消费
                      压缩后写入             history.jsonl 后
```
